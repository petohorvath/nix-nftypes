# Give the public API one set of naming and argument conventions

The 0.1.0 DSL mixed `flush*` builders with `verb.kind` namespaces, `snake_case` with camelCase field names, and positional with attrset arguments for the same fields. 0.2.0 applies one set of rules everywhere, so callers can predict a builder's shape from its kind:

- Each command verb is a `<verb>.<kind>` namespace, and each builder takes one object body. `add`, `create`, `delete`, `destroy`, `flush`, `list`, and `reset` are generated from the object-kind registry, and each offers only the kinds that nft runs as written for that verb. A verb with one kind is a namespace too, so its builder reads like nft's command: `insert.rule`, `replace.rule`, and `rename.chain`.
- Each builder has one name, in the namespace of what it builds. No builder or type is a second name for another, as `within` was for `inSet`, `match.eq` for `eq`, `expr.meta "mark"` for `fields.meta.mark`, `expr.mapRef "m"` for the bare `"m"` that `expr.map` and `vmap` take, and `types.matchStatement` for `types.statementOf [ "match" ]`. The top-level operators cover nft's seven match operators, so there is no `match` namespace; a caller that computes the operator writes the raw `{ match = { op; left; right; }; }`. No DSL name is both a statement and an expression constructor or a command verb: a statement whose tag one of them already names takes a `Stmt` suffix, as `setStmt`, `mapStmt`, and `resetStmt` do. An operator is named for the test it makes, as `hasAnyFlag` is for nft's `in`, which matches when any of the given flags is set, and a binary operator for the operation it computes, in camelCase as `builtins.bitAnd` is: `expr.bitAnd` and `expr.shiftLeft`. Expression constructors sit under `expr`, the payload ones (`expr.payload`, `expr.payloadRaw`, `expr.payloadTunnel`) included, and the compatibility helpers sit under `compatibility` with the tables they read. `compatibility` holds only what nft accepts on load: the placements nft allows and the Symbolic priorities it resolves at each hook. A consumer's convention built on those tables belongs to the consumer, so the library has no helper that derives a chain type from a priority or lists the hooks where an `oifname` match is useful.
- Every DSL field name is camelCase, and each field has one spelling. The DSL renames it to the JSON key, whether that key uses a hyphen (`queue-threshold`), an underscore (`rate_unit`), or no word break (`newname`, which the DSL spells `newName`). The field-word rule decides which word a field takes:
  - A field that holds statements, elements, or a key takes the DSL word for what it holds, `statement`, `statements`, `element`, `elements`, or `key`, whatever the JSON key is. A set's `elements` and `statements` stand for `elem` and `stmt`, and a rule's `statements` for `expr`, which would also read like the `dsl.expr` namespace. `setStmt` takes `element` and `mapStmt` takes `key` for the JSON `elem`, so `mapStmt { key; data; map; … }` reads like `expr.map key data`. `meter` applies one `statement`.
  - A field whose JSON key names something other than what it holds takes the DSL word for what it holds: `reject` takes `code` for the JSON `expr`, which holds the ICMP code, and a map body takes `dataType` for the JSON `map`, which holds the data type of the map's values.
  - Every other field keeps nft's JSON word, abbreviations included, so the DSL-to-JSON mapping stays obvious: a chain's `prio`, a ct expression's `dir`, a set statement's `op`, a chain's or flowtable's `dev`, and a quota object's `val`. `dev` takes one device or a list of them, as nft's `json_parse_devs` does, and `expr.jhash` keeps `expr`, which holds the one hashed expression.

  A statement, a command builder, and a table tree each throw for a JSON spelling and point to the DSL name. A name that is a Nix keyword takes a trailing underscore.

- A builder takes positional arguments only when every argument is required and there are at most two, as in `eq left right`, `vmap key data`, and `counter.ref name`. Every other builder takes one attrset. `dsl.table family name body` is the one exception, because it mirrors nftables' `table inet filter { … }`. The rule covers `dsl` builders, not the compatibility helpers: `compatibility.priorityValue family hook priority`, `compatibility.priorityName family hook priority`, and `compatibility.validChainPlacement family chainType hook` are lookups in the compatibility tables, and take the tables' three keys positionally. A field with one legal value is not an argument: nft's only flow operation is `add`, so `flow "ft"` takes the flowtable alone.
- A Field leaf is an expression nft loads as written in some rule, though the rule can need a table family or hook, as `fields.rt.nexthop` needs an ip or ip6 table. A key that nft loads only with a Refinement has no leaf, and its `expr` constructor builds it: a FIB result needs `saddr` or `daddr` among its flags, and every IPsec key and the conntrack keys `saddr`, `daddr`, `proto-src`, `proto-dst`, `ip saddr`, `ip daddr`, `ip6 saddr`, and `ip6 daddr` need a direction, so `expr.fib`, `expr.ipsec`, and `expr.ct` build them. The Refinement rules live in the schema bodies, so `validate` applies them to raw input too, and the constructors apply them by validating against those bodies. An `expr` constructor exists only for a form a leaf can't express, so meta, socket, and tunnel expressions, which take only a key, have their leaves only. A group of leaves for one keyed expression is named for its JSON tag, as `fields.ct`, `fields.meta`, and `fields.tunnel` are.
- A statement whose fields are all optional takes `{ }` for its empty form. Named variants cover forms an attrset cannot express: `.ref name` for a named object and `.auto` for the JSON null body. `counter` and `last` are not such statements: nft parses an inline counter only with both `packets` and `bytes`, and rejects an empty `last` body, so `counter { }` and `last { }` throw and point to `counter.auto` and `last.auto`. `reject { type?; code?; }` expresses every answer, so `reject` has no variant such as `reject.icmpx`.
- Every reference to a named object follows one rule. A builder takes the name with or without its `@` and emits the spelling nft's JSON parser looks up in that position: `"@name"` for a set, map, or flowtable, and the bare name for a stateful object, which nft looks up as written. A bare string where a reference is required either normalises under this rule or throws pointing at the reference builder; it never passes through. Every stateful object reference is a `.ref` variant, `ctHelper.ref "ftp"` as much as `counter.ref "c"`, and a statement with no other form throws when called. `expr.setRef` returns the `"@name"` string, which nft takes in a match, a map lookup, and a vmap, and lists; `inSet` needs it, while `expr.map`, `vmap`, `setStmt`, `mapStmt`, and `flow` add the `@` to a bare name themselves. A name that declares or selects an object is not a Reference and takes the bare name: `add.element`'s `name`, a Selector's `name`, and `meter`'s `name` drop a leading `@`, because nft looks up `@s` there as a set literally named `@s`, and a table tree throws on an object key that starts with `@`, such as `sets."@s"`, which would declare an object no Reference could name without ambiguity. The schema leaves a raw name as written.
- `delete`, `destroy`, `list`, `flush`, and `reset` take a Selector, which demands or accepts no field nft ignores for the verb. It holds the family, table, and name, or the handle where nft takes one, plus only the fields nft's parser reads for that verb and kind, such as a rule's `chain` or an element's `elements`. Each kind's Selector is a `select<Kind>Body` in the schema, or a `delete<Kind>Body` for a `delete` that takes exactly one of the name and the handle, and the command unions use it, so `validate` and the DSL reject the same values. A field nft ignores changes what the command does without an error: `delete set` with `elem` deletes the whole set. A field nft does require stays required: a rule's chain and positive handle, and an element's value.
- A body takes `handle` only where nft reads it: in a Selector, in `insert.rule` and `replace.rule`, which place or replace a rule by it, and in Read-back, where nft lists it. Every `add`, `create`, and `rename` body and every table-tree body rejects it, and the error points to Read-back. nft ignores a handle in those bodies, except on `add rule`, where nftables 1.1.6 ignores it and 1.1.7 places the rule after it, so a handle there did nothing or depended on the release, and the JSON and text forms disagreed about it: `add.table { handle = 4; }` kept its handle in JSON and lost it in text.
- Every library error starts `nix-nftypes: <API>: `, where `<API>` is what the caller called: a builder's path under `dsl` (`dsl.create.ctCount`), `dsl.table <family>.<name>` for a table tree, followed by the field's path in it, the renderer (`toJson`, `toText`, `toTextPretty`, `toTextBlock`, or `toTextBlockPretty`), `types.statementOf`, or a helper such as `compatibility.priorityValue`. A text renderer names itself, not its output form, so an error says which of the four raised it. The module system's own errors name the option path, which for a command or statement builder starts with the builder, as in `dsl.create.ctCount.name` or `dsl.log.level`. A text Refusal also ends with its field ([ADR 0004](0004-refuse-unsafe-text.md)).
- Every `types.*` name is camelCase, capitalised word by word, and spells its words out, as in `chainType`, `matchOperator`, `setOperator`, `flowOperator`, `ctDirection`, and `ipsecDirection`. A type name spells out a word even where the field it types keeps nft's abbreviation under the field-word rule, as `ctDirection` types `dir` and `setOperator` types `op`: a type is read without the field beside it, and abbreviating some names and not others left `setOp` beside `ctDirection`. A tag's name, such as `ct`, `ipsec`, or `numgen`, is a name, not an abbreviation, and stays as nft spells it. An enum or primitive type is named for its values when they mean the same wherever nft takes them (`comment`, `family`, `ifname`, `timeUnit`). Otherwise it is named for the tag or object kind whose field it types, then for that field (`chainPolicy`, `ipsecKey`, `numgenMode`, `ctDirection`, and `matchOperator`, not the bare `operator`); when several tags or kinds share the field, the name starts with what they share or with the first of them, as a shared body's does (`natFlag`, `setFlag`). A body namespace is named for what it holds (`expressionBodies`), a command's object union for its verb (`deleteObject`), and the body of one command for its verb and then its kind (`insertRuleBody`, `renameChainBody`, `selectSetBody`), so names that differ by a letter don't name different things. The Read-back object union is `readBackObject`.
- `types.expressionBodies`, `types.statementBodies`, and `types.objectBodies` hold bodies only, and every body is `<kind>Body`; the namespace tells the layers apart, as in `types.objectBodies.setBody` and `types.statementBodies.setBody`. A body that several tags share is named for what they share (`natBody`, `binaryOpBody`, `objectRefBody`, `verdictTargetBody`), or, without a common name, for the first of them (`masqueradeBody`, which `redirect` also takes). Every other body name puts its parent first: a variant or a nested part of one tag's body puts the tag first (`payloadRawBody`, `tcpOptionNamedBody`, `tunnelVxlanBody`), as the DSL does (`expr.payloadRaw`), and the body of one command puts its verb first (`flushRulesetBody`, `insertRuleBody`, `selectSetBody`). A command's body is named for its verb even when its fields match another body's, so `insertRuleBody` and the Read-back `ruleBody` are two types, not one type under two names. A body that both the expression and the statement layer take is listed in both namespaces, as `verdictTargetBody` is for the verdict expressions and for `jump` and `goto`. A statement body includes the statement's reference forms (`counterBody`, `ctCountBody`); its inline part alone is not exported. A tagged object is typed by its command's union (`addObject`, `insertObject`, `readBackObject`), not by a per-kind wrapper.

## Considered options

- Deprecated aliases with warnings, removed in a later release. 0.1.0 had been out for a day and had almost no users, so one clean break cost less than a deprecation cycle.
- Attrset arguments everywhere except operators. It would have changed `vmap` and `mangle`, which read like their nftables syntax when positional.
- A `match { left; op; right; }` builder for a computed operator. Each of its operators already has a top-level builder, so it would have been a second name for every one of them, and the raw attrset it would build is as short and passes the same rule validation.
- A table tree's top-level `elements` key for elements added apart from their set. It named each set twice, as `elements.s = { elements = [ … ]; }`, and block form had to refuse it, because nft's block grammar has no standalone `element` command. A set's `elements` covers a set the tree defines, and `add.element` one defined elsewhere.
- Plain functions for the single-kind verbs, `insert body` and `replace body`. They are shorter, but a builder's shape would then depend on how many kinds nft offers for its verb, and `rename.chain` was already a namespace.
- Stateful object references taken directly, as `ctHelper "ftp"`. `counter`, `quota`, `limit`, `synproxy`, and `ctCount` have inline forms that take an attrset, so they can't also take a name, and `.ref` was already the variant for a named object.
- Leaves that carry a direction in their path, as nft's text does: `fields.ct.original.saddr` and `fields.ipsec.in.reqid`. They would keep the short form, but FIB flags combine freely and fit no path, and adding such leaves later breaks nothing, so they wait for a need.
- One `reset` for the statement and the command verb, the statement as a `__functor` on the verb namespace. It kept the short name, but `reset` was then the one name that was both a statement and a command, and the `Stmt` suffix already resolved the same clash for `set` and `map`.
- A bare `last` value beside `lastUsed used`. The unseeded form stays short, but one statement had two names, and `counter` already carries the same two forms as `counter.auto` and `counter { … }`.
- JSON spellings passed through in object bodies, where the rename leaves unknown keys alone. A field then had two spellings in a table tree and a command builder but one in a statement, where the argument pattern rejected the JSON key without naming the DSL one.
- A rule's statement list kept as `expr`, or `expr` kept beside `statements` as an alias. Every 0.1.0 rule that names the field breaks, but 0.2.0 already breaks the DSL, and a later rename would have meant a second migration. An alias would have given the field two spellings; `expr` throws and points to `statements` like any other JSON spelling. The bare-list rule form, `rules = [ [ accept ] ]`, is unaffected.
- `match.in_`, after nft's operator token. `in` reads like set membership, which is `inSet`, and says nothing of the flag test.
- One reference shape everywhere, `"@name"`. nft looks a stateful object up by the name as written, so `counter "@c"` names no object; the spelling has to follow the position.
- Throwing when `vmap` or `expr.map` gets a list as its data. nft rejects a bare list there, but a list of key-value pairs is the obvious way to write a verdict map, and `inSet` already wraps a list in an anonymous set, so `vmap` and `expr.map` wrap one in an anonymous map, `{ set = list; }`, and only the schema rejects the bare list.
- Keeping `compatibility.chainTypeFor` and `compatibility.hooksWithOifname`, with `chainTypeFor` renamed to mark it a convention and `hooksWithOifname` indexed by family. They encode one consumer's conventions, not what nft accepts: nixos-nftzones was their only user, and an `oifname` match in `prerouting` loads but never matches. nixos-nftzones keeps its own copies.
- `priority` for a chain's `prio`. It reads better, but the field-word rule keeps nft's JSON word for every field that holds what its JSON key names, abbreviations included, so `dir`, `op`, `dev`, and `val` would have followed, and the DSL-to-JSON mapping would have stopped being obvious.
- Symbolic priorities on flowtables, as chains take them. The compatibility tables index priorities by a base chain's family and hook, while nft resolves a flowtable's symbol as netdev's at `ingress` whatever its table's family, so flowtables keep integer priorities and the DSL resolves only symbols the tables cover.
- Module-system errors that name a renamed field by its DSL name, such as `dataType` for the JSON `map`. The DSL renames a body before the schema checks it, so the module system names the JSON key, and naming the DSL field would need a second, DSL-named schema to check against.

## Consequences

- A bare `flush` value cannot also carry `flush.<kind>` builders, because the value is emitted as JSON. Flushing everything is therefore `flush.ruleset { }`, whose empty body stands for the JSON `null`. For the same reason the unseeded `last` is `last.auto`, not the bare `last`.
- `inSet` and `notInSet` take a set reference only as `"@name"`: their right side need not be a set, so a bare string is ambiguous and throws, pointing to `expr.setRef`.
- The DSL builds no statement that every tested `nft` rejects as input; a form that only a newer tested `nft` accepts keeps its builder ([ADR 0010](0010-accept-what-nft-loads-as-written.md)). `xt`, which nft lists for a legacy rule but refuses as JSON input, has no builder; `types.statementBodies.xtBody` types its Read-back.
- `expr.payloadRaw` and `expr.payloadTunnel` keep their names: `expr.payload` is a plain two-argument function, not a variant namespace that could carry `.raw`. The suffix matches `expr.tcpOptionRaw`.
